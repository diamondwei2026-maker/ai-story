# 跨章节一致性：指纹 + 事实簿双层机制

长篇小说的跨章一致性保障采用双层结构：ChapterFingerprint（情节层面匹配）+ FactSheet（事实层面校验）。

**Context**：用户可能在 DRAFTING 阶段手动修改第 33 章，而小说已生成到第 1000 章。若每次修改都让 AI 审查全部 1000 章，token 消耗不可承受。需要一种不依赖全量加载的一致性方案。

**Decision**：
- **ChapterFingerprint**——每章生成时自动提取约 200 tokens 的元数据（出场角色、关键情节节点、世界观元素）。用户修改章节后，AI 提取 ChangeFingerprint，通过数据库查询匹配受影响章节，而非逐章分析全文。
- **FactSheet**——项目级汇聚文件，存储角色状态、地点、时间线、关键物件等确切事实。生成新章时按关键词注入相关条目到 Prompt。内容与 FactSheet 冲突时自动标记。

**Considered Options**：
- 纯 AI 全文逐章分析：准确但不可规模化——1000 章 × 3K tokens/章 = 300 万 tokens 不可承受。
- 仅指纹：覆盖大结构（角色弧线、情节因果），遗漏小细节（主角住几楼、玉佩何时出现）。
- 仅事实簿：覆盖细节，但无法做情节影响传导。

**Consequences**：
- 指纹提取和事实提取每章需要额外的轻量 AI 调用（约 500 tokens 输入 + 200 tokens 输出），单章成本增加约 5%，但换取千章一致性保障。
- 事实簿使用乐观锁（version 字段）防止并发更新时的覆盖问题。
