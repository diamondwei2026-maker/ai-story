## 二、数据库设计

### 2.1 数据库选型

**MongoDB** — 选择原因：
- 章节正文（content）为长文本，MongoDB 的文档模型天然适配
- Beat Plan、Chapter Review 等字段为半结构化 JSON
- 变更分析（changeAnalysis）和审核结果（reviewResult）为嵌套文档
- 无需复杂 JOIN 查询

### 2.2 Prisma Schema

#### 枚举类型

| 枚举 | 值 | 说明 |
|------|------|------|
| ProjectStatus | IDEA, SETTING, OUTLINE, BEATS, DRAFTING, COMPLETED, ARCHIVED | 项目生命周期 |
| PhaseType | IDEA, SETTING, OUTLINE, BEATS, DRAFTING | 创作阶段 |
| StepStatus | PENDING, IN_PROGRESS, AI_GENERATING, AWAITING_REVIEW, REVIEWING, CONFIRMED, REJECTED | 步骤状态 |
| ChapterStatus | PENDING, DRAFT, PENDING_REVIEW, REVIEWING, COMPLETED, DISPUTED | 章节状态 |
| Severity | HIGH, MEDIUM, LOW, NONE | 影响严重程度 |
| ImpactStatus | PENDING, FIXED, SKIPPED, DEFERRED | 变更影响处理状态 |

## 三、API 接口设计

### 3.1 接口规范

- **Base Path**: `/`
- **请求格式**: JSON (Content-Type: application/json)
- **响应格式**: JSON
- **成功响应**: HTTP 200 (GET/PATCH) / 201 (POST 创建) / 200 (DELETE)
- **错误响应**: HTTP 400 (BadRequest) / 404 (NotFound) / 500 (InternalServerError)

### 3.2 项目接口

#### POST /projects — 创建项目

```
Request:
{
  "title": "string (required, non-empty)",
  "config?: { style?, platform?, genre?, defaultChapterWordCount? }
}

Response: Project
Status: 201
```

#### GET /projects — 获取所有项目

```
Response: Project[]
```

#### GET /projects/:id — 获取项目详情

```
Response: Project | 404
```

#### PATCH /projects/:id — 更新项目

```
Request: { title?, config?, status? }
Response: Project | 404
```

#### DELETE /projects/:id — 删除项目

```
Response: void | 404
```

#### POST /projects/:id/archive — 归档项目

```
Response: Project (status=ARCHIVED) | 404
```

#### POST /projects/:id/restore — 恢复归档项目

```
Response: Project | 404 | 400（仅 ARCHIVED 状态可恢复）
```

#### POST /projects/:id/complete — 完本

```
Request: { action?: "sync-and-complete" | "skip-and-complete" }
Response: { status: string, needsQueueResolution: boolean }
```

#### POST /projects/:id/reopen — 重新打开已完成项目

```
Response: { status: string }
```

### 3.3 阶段步骤接口（通用模式）

每个阶段（IDEA / SETTING / OUTLINE / BEATS）遵循统一 REST 模式：

```
GET    /projects/:id/steps/:phase            # 获取阶段数据
POST   /projects/:id/steps/:phase/generate   # 生成阶段内容
POST   /projects/:id/steps/:phase/confirm    # 确认阶段，进入下一阶段
POST   /projects/:id/steps/:phase/reject     # 驳回，重新生成
```

#### POST /projects/:id/steps/idea/generate — 生成灵感

```
Request:
{
  "idea": "string (创意描述)",
  "feedback": "string (可选，重生成时的用户反馈)"
}

Response: StepData
Side Effects:
  - 剥离 AI 可能输出的简介段落（保留纯卖点方案）
  - 自动执行合规检查（complianceCheck）
  - 状态: PENDING -> AI_GENERATING -> AWAITING_REVIEW
```

#### POST /projects/:id/steps/idea/generate-summary — 生成简介

```
Request:
{
  "selectedSellPoint": "number (required, 0-indexed 卖点序号)",
  "customBrief": "string (可选)"
}

Response: StepData
Side Effects:
  - 仅将选中的卖点内容传给 AI（非全量）
  - 生成一句话简介 + 500字简介
  - 剥离 AI 可能额外输出的卖点段落
```

#### POST /projects/:id/steps/idea/confirm — 确认灵感

```
Request:
{
  "selectedSellPoint": "number (required)",
  "customBrief": "string (可选)"
}

Response: StepData
Side Effects:
  - 项目状态: IDEA -> SETTING
  - 保存 selectedSellPoint 和 customBrief 到 review 字段
```

#### POST /projects/:id/steps/setting/generate — 生成设定

```
Request:
{
  "idea": "string (可选，来自 IDEA 阶段确认的简介)",
  "currentContent": "string (可选，重生成时的当前内容)"
}

Response: StepData
Side Effects:
  - 自动运行力量体系校验（powerSystemCheck）
  - 状态: PENDING -> AI_GENERATING -> AWAITING_REVIEW
```

#### POST /projects/:id/steps/outline/generate — 生成大纲

```
Request:
{
  "setting": "string (可选，设定集内容)",
  "structure": "string (默认: web-novel-ten)",
  "currentContent": "string (可选，重生成时的当前大纲)"
}

Response: StepData
Side Effects:
  - 自动运行：结构节奏分析、冲突分布检查、高潮点检测
  - 状态: PENDING -> AI_GENERATING -> AWAITING_REVIEW
```

#### POST /projects/:id/steps/outline/switch-structure — 切换结构

```
Request: { "structure": "string" }
Response: StepData
Side Effects:
  - 保留关键情节点种子（extractKeyPlotPoints）
  - 基于旧大纲 + 新结构重新生成
  - 重置为 AWAITING_REVIEW 状态
```

## 四、AI 服务集成

### 4.1 AI 模型架构

```
┌─────────────────────────────────────────┐
│              StepService                 │
│  (generateIdea / generateSetting / ...) │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│           AIGatewayService               │
│  - collectFullOutput(taskType, prompt)   │
│  - 统一错误处理                          │
│  - 超时重试策略                          │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│   DeepSeekChatModel (IChatModel)         │
│  - OpenAI SDK 适配                       │
│  - 模型别名映射                          │
│  - 流式输出 (AsyncIterable)              │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│        DeepSeek API                      │
│  - deepseek-chat (通用)                  │
│  - deepseek-reasoner (R1 深度推理)       │
└─────────────────────────────────────────┘
```

### 4.2 模型映射

| 别名 | 实际模型 | 用途 |
|------|---------|------|
| deepseek-chat | deepseek-chat | 通用内容生成 |
| deepseek-chat-v3 | deepseek-chat | V3 别名 |
| deepseek-r1 | deepseek-reasoner | R1 深度推理 |
| deepseek-reasoner | deepseek-reasoner | R1 深度推理 |

### 4.3 R1 推理模型使用策略

Beat 确认时通过 ADR-0007 三重判定自动判断哪些章节使用 R1（**满足任一条件即使用 R1**）：
- **结构位置**：开篇（第 1-3 章）或结局（最后 3 章）— BEATS 确认时自动计算
- **钩子密度**：`Beat.hookCount ≥ 3` — BEATS 生成时 AI 自动提取
- **高潮标记**：`Beat.isClimax = true` — 用户手动标记
- `useR1` 在 BEATS 确认时批量计算并固化到 Beat 文档中
- 其他章节使用 V3 通用模型

### 4.4 大容量 Beat 生成

当目标章节数超过阈值（BEATS_HIGH_VOLUME_THRESHOLD=35）时：
- 自动切换为 V3 模型（`deepseek-chat-v3`）+ `max_tokens=32768`
- R1 输出上限约 8K tokens，章数 >35 时存在截断风险；V3 32K 输出上限可覆盖 ≤90 章需求
- 章数 >90 走分批生成（按需实施）

### 4.5 TaskType 枚举

| TaskType | 用途 | 说明 |
|----------|------|------|
| IDEA | 灵感生成 | 卖点方案 + 简介 |
| SETTING | 设定生成 | 世界观/角色/关系 |
| OUTLINE | 大纲生成 | 剧情结构 |

## 五、上下文预算管理

### 5.1 三层上下文架构

```
┌──────────────────────────────────────────────┐
│            总 Token 预算: 8000                │
├──────────────┬──────────────┬────────────────┤
│ Global Static│Global Dynamic│  Local Context │
│   (3000)     │   (2000)     │    (3000)      │
├──────────────┼──────────────┼────────────────┤
│ 设定集输出    │ FactSheet    │ 当前 Beat      │
│ (时代/地理/   │ (角色状态/    │ + 前章摘要    │
│  社会/力量)   │  伏笔进度)    │ + 前章正文    │
└──────────────┴──────────────┴────────────────┘
```

### 5.2 预算计算流程

1. 独立硬上限：每层不超过限额
2. 总预算检查：三层总和不超过 8000 tokens
3. 优先级裁剪（超出时，从低优先级开始压缩）：
   - 首先从第三层（局部上下文）开始压缩
   - 其次第二层（全局动态）
   - 最后第一层（全局静态）

### 5.3 Token 估算

CJK 感知启发式算法：
- 中文字符：~1.8 chars/token
- ASCII 字符：~4 chars/token
- 使用 Unicode 码点范围精确区分

### 5.4 长章节上下文摘要

- 章节内容超过阈值（SUMMARY_THRESHOLD）时自动生成摘要
- 摘要目标：约 500 tokens
- 摘要维度：出场角色、关键事件、情感转折
- 后续章节优先使用摘要而非完整前章正文

## 八、内容审核系统

### 8.1 审核维度

ReviewService 对章节内容进行四维度 AI 审核：

| 维度 | 评分 | 关注点 |
|------|------|------|
| POLITICAL_SAFETY | 1-10 | 政治隐喻、敏感事件 |
| SEXUAL_CONTENT | 1-10 | 露骨描写、不当内容 |
| VIOLENCE | 1-10 | 血腥渲染、美化暴力 |
| VALUES | 1-10 | 负面价值观、歧视内容 |

### 8.2 审核结论与操作

| Verdict | 条件 | 可用操作 |
|---------|------|---------|
| PASS | 全部 >= 7 分 | 无（自动完成） |
| PASS_WITH_SUGGESTIONS | 有维度 5-6 分 | 采纳建议 / 忽略并确认 |
| NEEDS_REVISION | 有维度 3-4 分 | 采纳修改 / 手动修改 / 上诉 |
| BLOCKED | 有维度 <= 2 分 | 手动修改 / 上诉 |

### 8.3 上诉流程

1. 用户提交上诉理由
2. 验证：appealCount < 1（仅一次机会）
3. AI 重新审核：原始审核 + 章节内容 + 用户理由
4. 返回新审核结果
5. 更新 appealCount 和 appealedAt
6. 上诉后仍不满意：可 forceDispute 标记争议

## 九、变更分析系统

### 9.1 变更检测

ChangeAnalysisService.detectChangeType(original, updated)：
- **no-change**：内容完全相同
- **whitespace-only**：仅空白字符变化（归一化后相同）
- **minor**：编辑距离 < 50 且段落数不变
- **substantive**：编辑距离 >= 50 或段落结构变化

### 9.2 分析流程

1. 检测变更类型
2. 非实质性变更 -> 跳过
3. 实质性变更 -> AI 分析影响范围
4. 返回受影响章节列表（按严重程度分级）
5. 章节状态：COMPLETED/DISPUTED -> PENDING_REVIEW

### 9.3 定向修复

- 对每个受影响章节调用 AI 生成修复补丁
- 修复历史记录到 targetedFixHistory
- 支持 DEFERRED 状态（推迟修复）

## 十一、关键设计决策

1. **模块化架构**：NestJS 模块系统天然支持关注点分离
2. **Prompt 模板外置**：创作逻辑与 Prompt 解耦，非工程师可调整 Prompt
3. **三层上下文预算**：合理控制 Token 消耗，保证生成质量的同时控制成本
4. **CJK 感知 Token 估算**：精确的 Token 计数避免中文场景下的低估
5. **独立审核服务**：AI 独立审核模型，与创作模型解耦，保证合规判断客观
6. **FactSheet 队列机制**：异步消费事实更新，不阻塞章节确认流程
7. **变更分析指纹**：通过内容指纹去重，避免重复分析
8. **R1 智能分配**：按章节重要性选择性使用深度推理，平衡成本与质量
9. **Prisma + MongoDB**：文档数据库适配半结构化 AI 输出
10. **流式输出**：章节生成支持实时流式传输，改善用户等待体验
