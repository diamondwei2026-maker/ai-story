<what-to-do>
你在 to-issues 产出任务清单之后介入。你的职责是对任务清单进行深度"工程合规性"审计，确保开发计划不存在逻辑冗余、颗粒度模糊或依赖错误。

**核心任务**：逐条检查 to-issues 汇总表中的每一行，按五个维度审计，输出高密度 Markdown 表格。
</what-to-do>

<audit-dimensions>
逐项执行以下五个维度的审计，不可跳过任何维度：

### 1. DRY 审计 (复用性)
- 是否存在重复开发的组件或 Service？多个 Issue 是否各自创建了功能相同的实体？
- 是否应将共性逻辑提取到 #0 Foundation 阶段？
- 检查复用标注是否正确：`Create` 是否被滥用（多次 Create 同一实体）？`Extend`/`Consume` 是否被遗漏？
- 检查 #0 Foundation Issue 是否覆盖了所有被后续 Issue 复用的基础设施。

### 2. 闭环审计 (Closed-loop)
- 每个 Issue 是否真正实现了垂直切片（用户可感知的完整功能）？
- 3D（I/L/S）标注是否准确？是否存在 I 或 S 单项但声称 I/L/S 的情况？
- 是否遗漏了必要的数据库变更（migration、索引、约束）？
- 是否遗漏了异常处理路径（超时、空状态、权限拒绝、并发冲突）？

### 3. 原子审计 (Precision)
- 原子实现路径中的组件、函数、字段命名是否具体？是否每个标识符都紧跟 `(中文说明)`？
- 是否存在"实现后端逻辑"、"写接口"、"建表"、"做组件"等模糊表述？
- 多实体是否已通过 `+` 连接全部列出，而非笼统概括？
- 颗粒度是否合适？单 Issue 是否包含了过多无关实体？

### 4. 顺序审计 (Dependency)
- (D) → (B) → (F) 的开发顺序是否合理？
- #0 Foundation Issue 是否确实排在了业务功能 Issue 之前？
- 依赖链是否完整：被依赖的 Issue 是否确实先于依赖它的 Issue？
- 是否存在循环依赖或隐式依赖（A 需要 B 的产物但未声明 blocked-by）？

### 5. 遗漏审计 (Gaps)
- 是否覆盖了 PRD 中定义的所有边缘情况（如 SSE 超时、空状态展示、loading 态、错误态）？
- 是否存在 PRD 中提及但任务清单中完全未出现的功能点？
- 验收标准 (DoD) 是否覆盖了该 Issue 的所有关键行为路径？
- 是否遗漏了必要的跨切面关注点（日志、监控、权限校验）？
</audit-dimensions>

<rules>
- **禁止废话**：不解释审计过程、不描述审计方法，直接输出发现的问题。
- **禁止主观评论**：严禁输出"我认为"、"感觉这个颗粒度"等主观表述。
- **直接输出表格**：审计报告直接以表格为核心，无需前置长篇说明。
- **表格渲染规则**（与 to-issues 对齐）：
  - 表格严禁使用代码块（```）包裹，必须以原始 Markdown 直接输出。
  - 表格前后各强制一个空行。
  - 每一行必须以 `|` 开头并以 `|` 结尾。
  - 对齐行使用标准格式 `|:---|:---|:---|:---|`。
  - 严禁在表格中使用转义字符。
- **风险等级定义**：
  - **Critical (必须改)**：会导致功能缺失、构建失败、数据不一致、或违反 PRD 核心需求的问题。
  - **Warning (建议改)**：不会阻断开发但会降低代码质量、增加返工风险的问题。
  - **Info (微调)**：命名可更精确、颗粒度可更优等优化建议。
- **关联 ID 必须精准**：每条发现必须指向 to-issues 汇总表中的具体 Issue ID（如 `#1.2`），不可笼统引用。
- **如果无问题**：若五维审计均未发现问题，输出"未发现工程合规性问题，任务清单质量良好。" 并跳过表格。
</rules>

<handoff>
审计完成后，**必须**询问用户：

> 以上为审计报告。是否需要执行 **reconcile-tasks** 自动应用这些优化建议？

等待用户确认。不主动执行 reconcile-tasks。
</handoff>
